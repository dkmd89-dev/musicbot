# 5. ZIEL-ARCHITEKTUR

Der neue gemeinsame Helper:

  services/library_repair/maintenance_service.py

    def _resolve_within(
        base_path: Path,
        candidate: str,
        *,
        must_exist: bool = True,
    ) -> Path | None:
        """
        Löst candidate relativ zu base_path auf und stellt
        sicher, dass das Ergebnis STRIKT innerhalb base_path
        liegt (nicht base_path selbst).

        Liefert None, wenn:
          - candidate leer / nicht-String ist
          - candidate ein absoluter Pfad ist
          - das aufgelöste Ergebnis außerhalb base_path liegt
          - das aufgelöste Ergebnis base_path selbst ist
          - Path.resolve() an OSError/ValueError/RuntimeError
            scheitert (z. B. symlink loop, ENAMETOOLONG)
          - must_exist=True und das Ergebnis nicht existiert

        Wirft NIE nach außen.
        """

Aufrufer:

  artist_targets(artist: str) -> list[Path]:
      artist_dir = _resolve_within(self.library_root, artist)
      if artist_dir is None or not artist_dir.is_dir():
          return []
      return [...]

  album_targets(artist: str, album: str) -> list[Path]:
      artist_dir = _resolve_within(self.library_root, artist)
      if artist_dir is None:
          return []
      album_dir = _resolve_within(artist_dir, album)
      if album_dir is None:
          return []
      if not album_dir.is_dir():
          return []
      return [...]

  title-edit-Pfad:
      artist_dir = _resolve_within(self.library_root, artist)
      if artist_dir is None:
          return []
      track_path = _resolve_within(artist_dir, rel_path,
                                   must_exist=True)
      if track_path is None or not track_path.is_file():
          return []
      return [track_path]

Der bestehende _resolve_within_library() wird geprüft:

  Fall A: lässt sich als dünner Wrapper um _resolve_within()
          umbauen, ohne sein Verhalten zu ändern (seine
          Aufrufer bleiben kompatibel).
  Fall B: deckt eine andere Semantik ab (z. B. library-weit
          statt base_path-scoped) → dann bleibt er
          unverändert und _resolve_within() steht daneben.

Die Entscheidung A vs. B wird im Final Report begründet.
